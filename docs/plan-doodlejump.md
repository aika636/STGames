# План: игра «Дудл Джамп» (`doodlejump`)

Черновой план реализации новой мини-игры по контракту платформы (`docs/games.md`,
`src/registry.js`). Ничего из этого пока не реализовано — план только фиксирует решения
до того, как начнётся код. Ближайший аналог в кодовой базе — змейка
(`src/games/snake/`): та же связка «canvas + rAF-цикл + чистое ядро»; там же подсмотрены
конкретные приёмы (см. ссылки по тексту). Второй ориентир по конвенциям —
`src/games/minesweeper/` (двух-действийный ввод, сложность в настройках, банк форм
данных).

## 1. Геймплей

Вертикальный аркадный прыгун. Игрок управляет фигуркой, которая **скачет сама** —
никакой кнопки прыжка нет, — а игрок только двигает её влево/вправо, стараясь попадать
на платформы, которые появляются по мере подъёма камеры. Цель — набрать максимальную
высоту, пока фигурка не упадёт ниже нижнего края экрана.

Что берём из классики Doodle Jump:

- автопрыжок от каждой платформы, на которую фигурка приземлилась, двигаясь **вниз**;
- скролл камеры вверх, как только фигурка поднялась выше середины экрана — платформы,
  ушедшие вниз за край, исчезают;
- **wrap по горизонтали**: уйдя за левый край, фигурка появляется у правого, и наоборот
  (в оригинале так и есть; отдельно решать «включать ли» не нужно — это не спорная
  механика, как `wrapWalls` в змейке, а часть жанра);
- счёт = максимальная высота, до которой поднялась камера (не текущая позиция фигурки —
  спуск вниз после промаха счёт не уменьшает);
- проигрыш — фигурка падает ниже нижнего края экрана;
- несколько типов платформ вместо однородных (см. §3.3).

Что упрощаем сознательно (и почему):

- **никаких врагов, снарядов и стрельбы** — платформа STGames не имеет представления о
  «уроне» ни в одной другой игре, а монстры удваивают объём ядра и полностью новый набор
  тестов на столкновения. MVP без них уже полноценная играбельная петля.
- **никакого буста-полёта на ракете/пропеллере** — красивая, но необязательная механика;
  ей место в полировке, если останется время (см. Фазу 4), в MVP — нет.
- **наклон телефона (`deviceorientation`) не берём в MVP** — см. §4, отдельная оценка
  риска ниже.
- **без параллакс-фона и спрайтов** — как и в змейке, всё рисуется примитивами canvas
  (прямоугольники/дуги), это соответствует визуальному языку остальных игр платформы
  (судоку, сапёр, нонограмма — тоже геометрия, не картинки, кроме нонограммы, у которой
  картинка — сама суть игры).

## 2. Ядро — `src/games/doodlejump/core/`

Без DOM, без `document`, без `Math.random()` внутри (только через переданный `rng`) —
как и требует правило 1 в `docs/games.md`. Тестируется под `node`.

### 2.1. Единицы измерения

Мир живёт в «условных пикселях мира» (world units, сокращённо wu) — не в CSS-пикселях и
не в клетках, как у судоку/змейки. Экран (canvas) — окно фиксированной **логической**
ширины `WORLD_W = 400` wu и произвольной по факту высоты `WORLD_H` (по умолчанию 640,
портретное соотношение ~0.625, как у телефона), которое `ui/view.js` масштабирует под
реальный размер контейнера (см. §3.1). Это тот же приём, что у canvas судоку/сапёра —
поле в «своих» единицах, DPR и подгонка размера — забота `ui/`.

Гравитация и импульс прыжка — константы в wu/с и wu/с², не в px: это отвязывает физику от
экрана и позволяет тестировать её без DOM.

```js
export const WORLD_W = 400;
export const GRAVITY = 2200;       // wu/с², вниз
export const JUMP_VELOCITY = -900; // wu/с, вверх (отрицательный y — вверх, как в canvas)
export const PLAYER_W = 40;
export const PLAYER_H = 40;
```

Подбор чисел — эмпирический (как `START_MS`/`SPEEDUP_MS` у змейки): цель — прыжок высотой
примерно в 2.5–3 своих роста фигурки, чтобы разрыв между платформами был терпимым при
плотности платформ по умолчанию. Значения фиксируются в Фазе 1 и правятся по ощущениям
при ручной проверке (Фаза 4), а не выводятся аналитически.

### 2.2. Фиксированный шаг физики

Как в змейке (`onFrame` в `src/games/snake/index.js:227`) — `requestAnimationFrame` с
накоплением времени, но здесь физика непрерывная (не тиковая), поэтому схема иная: **fixed
timestep с накоплением остатка**, стандартный паттерн для платформеров, чтобы столкновения
не зависели от частоты кадров браузера.

```js
export const STEP_MS = 1000 / 120; // 120 Гц физики — с запасом от 60 Гц экрана

// state.accumulatorMs копит остаток между кадрами; step() гоняет внутренний
// подшаг ровно STEP_MS, пока накопитель не иссякнет (защита от «спирали смерти» —
// не больше MAX_SUBSTEPS подшагов за один вызов).
export function advance(state, dtMs, input) { ... }
```

`ui/`-слой на каждый rAF зовёт `advance(state, dtMs, input)` — единственную функцию входа
для игрового времени; `advance` сама решает, сколько внутренних `stepOnce()` прогнать.
Разделение на `advance` (обёртка с накопителем) и `stepOnce` (один физический подшаг)
нужно ровно затем, чтобы тесты ядра могли гонять `stepOnce` впритык, без таймеров и без
накопителя — детерминированно, шаг в шаг.

### 2.3. Форма `state`

```js
{
  world: { w: WORLD_W, h: WORLD_H },
  player: { x, y, vx, vy, facing: 1 | -1 },  // facing — для отрисовки, не для физики
  platforms: [
    { id, x, y, w, kind: 'normal' | 'moving' | 'crumbling' | 'spring', // MVP: первые два
      vx?,               // только у 'moving' — горизонтальная скорость
      broken?: boolean,  // только у 'crumbling' — сломалась под ногами
    },
  ],
  cameraY: 0,        // мировая y верхнего края видимой области; убывает по мере подъёма
  score: 0,           // = максимальная высота, целое
  best: 0,            // не используется ядром для рекордов (это дело core/stats.js),
                       // но полезно самому экрану знать текущий сеансовый максимум
  alive: true,
  nextPlatformY: ...,  // граница, ниже которой генератор ещё не «настелил» платформы
  input: { dir: -1 | 0 | 1 },  // текущее намерение игрока, ставится setInput()
  accumulatorMs: 0,
  rng,                 // держим ссылку на функцию rng в состоянии — нужно генератору
                        // платформ по мере подъёма камеры, а не только при createGame()
}
```

Ключевое решение: **`y` растёт вниз** (как в canvas и как в змейке `dir.y`), а не вверх —
меньше сюрпризов при переносе координат в `ui/view.js`. Высота/счёт считается как
`-cameraY` (или другая монотонно растущая величина от начальной точки), а не как «сколько
платформ пройдено» — иначе платформа типа `spring`, дающая двойной прыжок, ломала бы
пропорциональность счёта и физической высоты.

### 2.4. Сигнатуры

```js
export function createGame({ rng = Math.random, worldH = 640 } = {}) -> state
export function setInput(state, dir)              // dir: -1 | 0 | 1, мгновенно (не очередь,
                                                     // в отличие от setDirection() змейки —
                                                     // здесь непрерывное аналоговое намерение,
                                                     // а не дискретный ход)
export function advance(state, dtMs) -> { landed, brokeplatform, fell }  // тиковые флаги
                                                     // для звука/статистики, как step() змейки
export function stepOnce(state)                    // один физический подшаг STEP_MS,
                                                     // используется advance() и тестами
export function ensurePlatformsAbove(state, targetY) // достраивает генератор до нужной
                                                     // высоты — вызывается из advance()
                                                     // каждый подшаг, дёшево при малом shift
```

### 2.5. Генерация платформ

Процедурная, **seeded PRNG** — тот же `mulberry32`, что у судоку и змейки (копия функции
в `core/rng.js` игры, не импорт из чужой игры — правило проекта «игры друг у друга ничего
не берут», см. `docs/development.md` про клавиатуру балды). Генератор работает **потоково
вверх**: при каждом продвижении камеры (`ensurePlatformsAbove`) достраивает ряд новых
платформ выше текущей верхней сгенерированной точки, а не создаёт сразу всё поле — иначе
партия была бы конечной или потребовала бы огромный массив платформ впрок.

**Ограничение достижимости — самое важное решение генератора.** Вертикальный зазор между
соседними платформами по одной вертикальной полосе не должен превышать максимальную
высоту прыжка `maxJumpHeight = JUMP_VELOCITY² / (2·GRAVITY)`, иначе игра тихо ломается —
платформы стоят, а допрыгнуть до части из них нельзя. Берём с запасом
(`maxGap = maxJumpHeight * 0.82`), запас — под манёвр по горизонтали (пока фигурка летит
вбок, часть вертикальной скорости «не работает» на высоту доступного прыжка нет, но само
время полёта даёт горизонтальный запас; 0.82 — эмпирический коэффициент, поправляется по
ощущениям в Фазе 4, тест на достижимость фиксирует **инвариант**, а не точное число).
Горизонтально позиция следующей платформы берётся случайно в пределах `WORLD_W`, без
ограничения на «достижимость по x» — из-за wrap по краям экрана игрок всегда может дойти
до любой точки по горизонтали, пока падает; единственный реальный лимит — вертикальный.

### 2.6. Типы платформ

MVP (Фаза 1):

- **`normal`** — стоит на месте, прыжок обычной силы.
- **`moving`** — едет влево-вправо между `x` и `x + w`-зеркальными границами экрана,
  отражаясь от `0`/`WORLD_W` (не от wrap — платформа физически едет, а не телепортируется).

Полировка (Фаза 4, если останется время — иначе документируется как «не сделано»):

- **`crumbling`** — рассыпается через `N` мс после приземления (флаг `broken`, дальше не
  участвует в столкновениях; убирается из `state.platforms` при выходе за камеру).
- **`spring`** — даёт `JUMP_VELOCITY * 1.6` вместо обычного — используется как «клапан
  давления» генератора: изредка появляется там, где обычный зазор был бы близок к пределу
  достижимости, что расширяет вариативность уровня без риска недостижимых мест.

Явно НЕ берём (даже в полировке) — движущиеся платформы с телепортом, платформы-триггеры
ловушек, монстров: см. §1 про сознательные упрощения.

### 2.7. Столкновения

Детект — **только при движении вниз** (`vy > 0`) и только когда игрок пересекает
верхнюю грань платформы сверху вниз между предыдущим и текущим подшагом (свипing по
`y`, не point-in-rect на одном кадре — иначе при высоком `vy` и низком FPS фигурка может
«проскочить» тонкую платформу за один кадр, классическая проблема туннелирования в
дискретной физике). Прямоугольник платформы — AABB, горизонтальное пересечение — обычное
условие по `x`/`w`. Приземление на **любую** живую платформу мгновенно даёт
`vy = JUMP_VELOCITY` (или `*1.6` для `spring`), кроме `crumbling`, у которой оно тоже
даёт прыжок, но затем платформа помечается `broken` и больше не участвует в столкновениях.

### 2.8. Проигрыш

`state.alive = false`, когда `player.y - cameraY > worldH` (фигурка ушла ниже нижнего
края видимой области с запасом на её высоту). Camera не откатывается назад никогда —
даже во время падения вниз счёт (максимальная высота) остаётся зафиксированным, а
`cameraY` продолжает следовать за игроком вниз ровно настолько, чтобы можно было увидеть
момент падения за край (иначе экран замирал бы на пустом верхе, и игрок не понимал бы,
что произошло).

### 2.9. `core/stats.js`

Формат по образцу змейки/сапёра — `{ played, bestHeight, bestStreak }` или проще, по
аналогии со змейкой: `{ played, bestScore }`, где `bestScore` = лучшая высота. Второй
показатель — не «длина» (у прыгуна нет аналога), а, например, `bestPlatforms` — число
платформ, на которые успешно приземлился за один заезд (аналог «длины» змейки: тоже
косвенный показатель мастерства, отличный от чистого счёта). Итог поля: `{ played,
bestScore, bestPlatforms }`. `readStats`/`recordPlayed`/`recordResult`/`resetStats` —
одна в одну по контракту `src/games/snake/core/stats.js`, отдельный модуль (игры не
импортируют чужой `core/stats.js` — тот же принцип, что у сапёра/нонограммы).

## 3. Отрисовка — `src/games/doodlejump/ui/view.js`

### 3.1. Canvas и портретный формат

Буфер canvas — в **device-пикселях** (`canvas.width = cssW * devicePixelRatio`), как у
змейки (`src/games/snake/ui/view.js:36`), иначе на телефоне мыло. В отличие от змейки поле
не квадратное, а портретное: контейнер задаёт `aspect-ratio` через CSS (кроссворд уже
полагается на `aspect-ratio`/`container-type`, см. `docs/development.md` — «в jsdom не
считаются вовсе», поэтому и здесь размер/пропорции проверяются e2e, не jsdom). Логическая
ширина мира (`WORLD_W`) при отрисовке масштабируется в CSS-пиксели одним коэффициентом
`scale = canvas.width / WORLD_W`; высота видимой области (`worldH` в wu) подбирается так,
чтобы при типичной ширине окна попапа (~340–400 CSS px) на экране помещалось 5–7
платформ по высоте.

`draw(state)` рисует относительно `state.cameraY`: `screenY = (worldY - cameraY) * scale`.

### 3.2. Требование к jsdom

`canvas.getContext('2d')` в jsdom без пакета `canvas` — `null`. Как у змейки: `draw()`
проверяет `ctx2d` и становится no-op при отсутствии контекста, экран продолжает жить.
UI-тесты под jsdom (см. §6.2) подменяют `HTMLCanvasElement.prototype.getContext`
записывающей заглушкой по образцу `tests/snake/ui.test.mjs:36-51`, чтобы видеть смещения
через `fillRect`/`arc`.

### 3.3. Переменные `--stg-doodlejump-*`

Заводятся в блоке «Палитра» `style.css`, **литералами и `var()`, без `color-mix()`** — то
же ограничение, что у `--stg-snake-*` (`style.css:239-241`, `docs/development.md`
«color-mix() не доезжает до JS»): их читает `getComputedStyle` в JS для `fillStyle`.

```css
--stg-doodlejump-player: var(--SmartThemeQuoteColor, #6ca0dc);
--stg-doodlejump-platform: var(--SmartThemeBorderColor, #888);
--stg-doodlejump-platform-moving: #7fae5a;   /* смысловой цвет — тип платформы, литерал */
--stg-doodlejump-platform-crumbling: #b58a4a;
--stg-doodlejump-spring: #e0c34d;
```

По аналогии со змейкой — свои значения в блоках `[data-stg-theme='light']` и
`[data-stg-theme='dark']` (переменные без смысловой нагрузки берут из общего слоя `--stg-*`
там, где можно — например, платформа `normal` вообще может красится через `--stg-line-strong`
напрямую без своей переменной, если не несёт смысла; типовые же цвета платформ (`moving`/
`crumbling`/`spring`) — смысловые и фиксированные, как цифры сапёра, в палитру не входят
(правило из `docs/games.md`, п.6, исключение «цвет, который несёт смысл»).

### 3.4. Что рисуется

- фигурка — прямоугольник или скруглённый прямоугольник с «глазами»-точками, которые
  смотрят по `facing` (простая деталь, дающая ощущение направления без спрайтов);
- платформы — прямоугольники, цвет по `kind`; `crumbling` с `broken: true` — полупрозрачная
  или с трещиной (паттерн из двух-трёх коротких линий);
- счёт — текстом поверх canvas через `ctx.fillText`, как аналог шапки змейки, либо
  HTML-элемент над canvas (см. §4 про `snake-header`-подобную шапку) — решение в пользу
  HTML-шапки: текст на canvas не масштабируется чётко при DPI-скейле и плохо стилизуется
  через `--stg-*`, HTML-элемент решает обе проблемы бесплатно.

## 4. Управление — `src/games/doodlejump/ui/controls.js`

Клавиатура — общий скелет (`document`, capture-фаза, гасятся только обработанные клавиши,
Esc не трогается) — как у змейки/слов/балды. В отличие от змейки, ввод не дискретный ход,
а **непрерывное намерение** (зажатие клавиши держит `dir`, отпускание сбрасывает в 0):
нужны и `keydown`, и `keyup`.

```
ArrowLeft/ArrowRight, A/D, Ф/В (ЙЦУКЕН) — движение влево/вправо, держать
Space / P / З — пауза
Enter — рестарт после проигрыша
```

`keyup` обязателен и должен снимать `dir` **только если отпущенная клавиша совпадает с
той, что его установила** — иначе быстрый оверлап нажатий (влево ещё держится, вправо уже
отпущено) даст рывок в обратную сторону. Практически удобнее держать два флага
`leftDown`/`rightDown` и выводить `dir` из их комбинации (стандартный приём для
непрерывного платформерного управления), а не хранить единственное «последнее нажатое
направление», как в змейке.

Экранные кнопки влево/вправо — обязательны по той же причине, что d-pad змейки и ряд
цифр судоку: не про наличие поля ввода (тут его и не нужно), а про удобство игры одной
рукой на телефоне и про паритет с десктопом. Кнопки шлют `mousedown`/`touchstart` → `dir`,
`mouseup`/`touchend`/`mouseleave` → сброс — те же грабли гонки, что у клавиатуры, и то же
решение (флаги, не «последнее событие»).

**Наклон (`deviceorientation`)** — оценка: НЕ включать в MVP и, вероятно, не включать
вовсе без явного запроса. Причины:
1. `deviceorientation` требует разрешения пользователя на iOS 13+
   (`DeviceOrientationEvent.requestPermission()`), а окно игры открывается внутри попапа
   ST — нет собственной кнопки "разрешить датчики" в UX платформы, и без явного жеста
   пользователя API вызвать нельзя (спонтанный вызов из `mount()` браузер отклонит).
2. Ни у одной другой игры платформы нет прецедента работы с сенсорами устройства — это
   первый такой случай, ломающий чистоту принципа «UI не знает о специфике устройства
   сверх touch/mouse/keyboard».
3. Кнопки + свайп достаточно закрывают тач-сценарий; выигрыш от наклона субъективен и не
   стоит добавляемой сложности (лишний permission-флоу, лишняя ветка кода, недоступная
   в e2e-тестах — Playwright не эмулирует `deviceorientation` без доп. протокола).

Итог: наклон — не делаем, фиксируем решение и причину в этом плане, чтобы не переоткрывать
вопрос без повода.

**Пауза при потере видимости** — как у змейки (`visibilitychange`/`blur`/`focus`,
`src/games/snake/index.js:255-275`): обязательна, физика на непрерывном времени иначе
даст фигурке при возврате на вкладку огромный `dtMs` и мгновенную смерть.

**Свайп** — по аналогии с змейкой (`attachSwipe`) не подходит (там дискретные повороты),
но простое **точечное касание/удержание половины экрана** (тап по левой половине canvas
= держать влево, по правой = держать вправо, аналог экранных кнопок, но без отдельных
DOM-элементов) может дублировать кнопки — решение оставить на Фазу 2, не критично для
MVP: сначала кнопки, тач по canvas — опциональное удобство при живой проверке.

## 5. `index.js` игры

Контракт (`id`, `title`, `tagline`, `icon`, `defaults`, `slash`, `mount`,
`renderSettings`, `renderStats`) — по образцу `src/games/snake/index.js`.

```js
const DEFAULTS = Object.freeze({
  stats: {},
  difficulty: 'normal',   // 'easy' | 'normal' | 'hard' — плотность/ширина платформ
  movingPlatforms: true,  // показывает ли генератор 'moving' в MVP
  showButtons: true,      // экранные кнопки влево/вправо (десктоп может их скрыть)
});

export default {
  id: 'doodlejump',
  title: 'Дудл Джамп',
  tagline: 'Прыгай выше — не упади',
  icon: 'fa-solid fa-shoe-prints',  // точный класс подобрать по каталогу Font Awesome,
                                     // доступному в ST 1.18.0 — проверить на живой инсталляции
  defaults: DEFAULTS,
  slash: { name: 'doodlejump', help: 'Открыть игру «Дудл Джамп»' },
  mount(root, api) { return createDoodleJumpScreen(root, api); },
  renderSettings(container, api) { /* select сложности, чекбоксы */ },
  renderStats(container, api) { /* сыграно / лучшая высота / лучший забег по платформам */ },
};
```

`difficulty` — как у сапёра/нонограммы/кроссворда: влияет на параметры генератора
(плотность платформ, доля `moving`, средний зазор относительно `maxGap`), а не на
геометрию, как у судоку. Значение — живая настройка, читается генератором на каждом
`ensurePlatformsAbove()`, так что смена сложности посреди партии подхватывается для
**новых** платформ выше текущей позиции (симметрично тому, как `wrapWalls` змейки
применяется «с этого тика», не дожидаясь рестарта — `docs/development.md`, раздел
«Змейка — режим стен»).

Партия **не сохраняется**, аналогично змейке — падение ниже экрана и есть естественный
конец заезда, а пауза при потере вкладки делает персистентность ненужной (см.
`docs/development.md`, «Змейка — заезд не сохраняется»). В `settings` остаются только
`stats` и настройки.

## 7. Тесты

### 7.1. Ядро — `tests/doodlejump/engine.test.mjs`

- `mulberry32` даёт одинаковую партию на одном сиде: сыграть N подшагов с фиксированным
  `input` расписанием на двух `createGame({ rng: mulberry32(seed) })` — история координат
  и счёта совпадает (по образцу «одинаковый seed даёт одинаковые партии» в
  `tests/snake/engine.test.mjs:256-276`).
- Физика прыжка: свободное падение без платформ — `vy` растёт по `GRAVITY * dt`;
  приземление на `normal` платформу мгновенно даёт `vy = JUMP_VELOCITY`; на `spring` —
  `*1.6`; `crumbling` даёt прыжок один раз и помечается `broken`.
- Столкновения: приземление засчитывается только при движении вниз — фигурка, летящая
  вверх сквозь платформу снизу, её не задевает; свип-проверка ловит платформу, которую
  один грубый дискретный шаг проскочил бы насквозь (тест намеренно берёт большой `dtMs`
  и тонкую платформу).
- Wrap по горизонтали: `x < 0` → появление у `WORLD_W`, и обратно, скорость и `y` не
  меняются.
- Проигрыш: `alive` становится `false` строго когда `player.y - cameraY` превышает
  `worldH` с запасом на высоту фигурки, не раньше.
- Счёт монотонен: `score` не уменьшается при спуске фигурки вниз после промаха ни при
  каких дальнейших действиях до конца партии.
- Генерация достижимых платформ: прогнать `ensurePlatformsAbove()` до большой высоты на
  нескольких сидах и проверить инвариант — для каждой сгенерированной платформы найдётся
  предыдущая (по возрастанию высоты) в пределах `maxGap` по вертикали (не обязательно
  строго «предыдущая по индексу» — платформы на близкой высоте считаются одним «этажом»);
  это главный тест-регрессия против «тихо сломанной» игры, аналог теста решаемости
  нонограммы/кроссворда (`tests/nonogram/pictures.test.mjs`, `docs/development.md` про
  требование «решается линейными выводами»).
- `core/stats.js`: `readStats`/`recordPlayed`/`recordResult`/`resetStats` — набор тестов
  один в один по образцу `tests/snake/engine.test.mjs:278-337` (нормализация битых
  значений, `resetStats` мутирует на месте, `recordPlayed` не создаёт запись при чтении).

### 7.2. UI под jsdom — `tests/doodlejump/ui.test.mjs`

По образцу `tests/snake/ui.test.mjs`: свой jsdom, заглушка `getContext('2d')`,

## 9. Риски и грабли

- **rAF в модалке поверх чата ST.** Как и у змейки, окно живёт поверх активного чата
  таверны — лишний тяжёлый цикл (canvas на 60 Гц с непрерывной физикой, а не тиковой раз
  в 70–170 мс, как у змейки) заметнее нагружает CPU/GPU вкладки. Смягчение: `advance()`
  ограничивает число подшагов на кадр (`MAX_SUBSTEPS`), отрисовка — простые примитивы без
  теней/градиентов.
- **Утечка слушателей при `destroy()`.** Больше слушателей, чем у змейки: `keydown` +
  `keyup` (не один `keydown`), плюс обработчики на двух кнопках (`mousedown`/`mouseup`/
  `mouseleave`/`touchstart`/`touchend`), плюс `visibilitychange`/`blur`/`focus`. Каждый
  обязан сниматься в `destroy()`; тест на «после destroy() событие больше не гасится»
  обязателен (как в `tests/snake/ui.test.mjs:204-212`), и стоит завести список слушателей
  в замыкании, чтобы не забыть один при снятии — риск реальный именно из-за их числа.
- **Конфликт клавиш с полем ввода чата.** Общее правило — гасить только обработанные
  клавиши на capture-фазе; специфика тут — `keyup` тоже должен проверять
  `isInteractiveTarget`/фокус, иначе отпускание стрелки после фокуса на постороннем
  элементе (например, после клика по кнопке паузы) может «залипнуть» с `preventDefault`
  там, где его быть не должно.
- **Непрерывное движение и `keydown` autorepeat.** Браузер шлёт повторные `keydown` при
  зажатой клавише (autorepeat) — если логика наивно переключает `dir` по каждому
  `keydown`, лишних эффектов не будет (значение то же), но стоит не полагаться на
  «однократность» `keydown`, как это в некоторых местах допустимо у змейки (там `keydown`
  — дискретный ход, autorepeat игнорируется естественным образом через очередь).
- **Мыло на мобильных без учёта `devicePixelRatio`.** Как у змейки — решается тем же
  приёмом (`canvas.width = cssW * devicePixelRatio`), но здесь портретный, а не квадратный
  канвас: пересчёт размера при ресайзе окна (поворот телефона) должен пересчитывать и
  `cssW`, и `cssH` независимо, не полагаясь на «поле квадратное», как у змейки
  (`src/games/snake/ui/view.js:33-38` — этот код для нового формата не годится буквально,
  писать заново).
- **Светлые темы ST и палитра.** Строго следовать правилу «цвета только из `--stg-*`» —
  прямое обращение к `--SmartThemeQuoteColor`/`--black30a` в игре запрещено (см. §3.3);
  проверить на живой инсталляции во всех трёх режимах палитры (`theme`/`light`/`dark`),
  как это сделано для остальных игр в Фазе 14 (`docs/development.md`, чеклист
  «Оформление»).
- **Воспроизводимость тестов без `Math.random`.** Всё, что решает исход партии
  (расположение платформ, тип платформы), обязано идти через переданный `rng`; в
  браузере — `Math.random`, в тестах — `mulberry32(seed)`. Нарушение этого правила в
  генераторе платформ убьёт тест на детерминизм партии (§7.1) — тест нужно писать сразу,
  а не постфактум, чтобы поймать нарушение немедленно.
- **Генерация недостижимых платформ.** Главный риск жанра «прыгуна»: без явного
  ограничения `maxGap` относительно физически возможной высоты прыжка процедурный
  генератор рано или поздно поставит два «этажа» платформ дальше друг от друга, чем можно
  допрыгнуть, — игра станет непроходимой без предупреждения (в отличие от смерти,
  ощущается как баг, а не как проигрыш). Тест на инвариант достижимости (§7.1) — не
  опциональный, это условие «игра вообще работает», как решаемость нонограммы/кроссворда.
- **Оценка сложности констант физики умозрительна.** `GRAVITY`/`JUMP_VELOCITY`/плотность
  платформ подбираются на глаз и почти наверняка потребуют правки после первой живой
  проверки (Фаза 4) — план сознательно не фиксирует финальные числа, только структуру и
  единицы измерения.
- **Наклон устройства отложен без реализации** (см. §4) — если пользователь впоследствии
  попросит его добавить, потребуется отдельная оценка permission-флоу для iOS и то, как
  вписать разрешение в UX попапа ST (кнопка внутри игры, отдельная от системного диалога).
